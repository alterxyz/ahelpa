# 性能

这一页讲两件事：helper 起来要多快，以及它做完后 ahelpa 多快能察觉。数据来自一台 macOS 机器，会随网络和服务商负载波动，请当作参考值，不是保证。

## 测什么

每次启动，时间都是从执行 `ahelpa launch` 开始算的秒数：

| 列 | 含义 |
| --- | --- |
| `launch` 返回 | helper 已经起来，并确认收到了任务。这就是启动时间。 |
| 写完结果 | `summary.md` 写完的时刻，大致等于模型干完活。 |
| `wait` 返回 | 在「写完结果」之后，还要等模型发收尾消息、进程退出，再等 daemon 察觉到完成。 |

从「写完结果」到「`wait` 返回」之间有两段：
- 模型收尾并退出，这一段由 harness 决定；
- daemon 在下一次轮询时察觉到完成，这一段由 ahelpa 决定。

daemon 每 3 秒轮询一次，所以 `wait` 返回的时刻会扎堆在轮询周期的整数倍上。下文就用这个间隔来测量轮询周期。

## 基准线

2026-11-06 定。

- **启动参考值 4.5 秒**，指 `launch` 返回的时间。某个名字持续超过 **6 秒**，就可能退步了，值得查。有些名字本来就启动得更快，比如 `deepseek-pi` 和 `kimi`。
- **daemon 轮询周期约 3 秒**，用 `wait` 返回时刻扎堆的间隔来衡量。这样 helper 退出后，最多再过一个轮询周期就会被察觉。这个周期不能随会话记录增多而变长。

## 怎么测

```bash
bash scripts/startup-bench.sh --project /path/to/trusted/repo
```

- 脚本用默认 role 和默认模型启动每个对外名字，任务很简单：在 `summary.md` 里写一行 `ok`。
- 一次只跑一个 helper，每轮换一个起始名字，默认跑 3 轮。
- 结果写成 CSV（`--out`，默认 `startup-bench.csv`），并打印中位数。
- 只测部分名字时，把名字列在后面，比如 `bash scripts/startup-bench.sh deepseek deepseek-pi`。
- 会调用真实模型。
- 要用 helper 已经信任过的项目目录，Claude 遇到不受信任的目录会直接拒绝。
- 完整跑一遍大约 10 分钟。

## 最新结果（2026-11-07）

每个名字跑 3 次，取中位数，单位是秒；都用默认模型和上面那个简单任务。`gemini`、`mistral`、`deepseek`、`deepseek-pi` 是改跑各自 TUI 之后在 v0.12.0 上测的；`claude`、`codex`、`kimi` 来自当天修复轮询之后的那一轮。

| 名字 | `launch` 返回 | 写完结果 | `wait` 返回 |
| --- | --- | --- | --- |
| `claude` | 4.3 | 8.4 | 12.3 |
| `codex` | 5.0 | 11.8 | 15.3 |
| `gemini` | 2.4 | 16.6 | 40.8 |
| `kimi` | 2.9 | 10.3 | 15.3 |
| `mistral` | 4.5 | 7.2 | 15.3 |
| `deepseek` | 4.4 | 10.7 | 15.4 |
| `deepseek-pi` | 1.9 | 5.3 | 9.3 |

全部成功。`wait` 返回的时刻扎堆在 daemon 轮询周期（约 3 秒）的整数倍附近。写完结果到 `wait` 返回之间，主要是模型在收尾，不在 ahelpa。`gemini` 波动最大（`wait` 24.5–51.8 秒）：它改完 `summary.md` 之后还在继续思考（存档的一屏显示打出 `[AHELPA:DONE]` 前有「Thought for 7.5s」），没有触发完成提醒。

## `deepseek` 对比 `deepseek-pi`

| | `deepseek`（Vibe，走 Mistral 订阅） | `deepseek-pi`（Pi，走 DeepSeek API） |
| --- | --- | --- |
| 启动（`launch` 返回） | 4.4–4.9 秒 | 0.8–1.9 秒 |
| 简单任务（`wait` 返回） | 10.6–15.4 秒 | 6.3–10.0 秒 |
| 同一道对抗复核题（同一份任务书、同一份代码快照） | 9.1 分钟 | 24.9 分钟 |
| 4 道有边界的真实任务（[案例](case-deepseek-trial-20261106.md)） | 每题 2.6–5.7 分钟 | 每题 2.6–8.8 分钟 |
| 复核发现 | 发现回退没有日志，另有两个小问题 | 还发现了出错时用旧快照对账、关键顺序没有测试守着 |
| 观察到的可靠性 | 没有遇到服务商报错 | 有一次 DeepSeek API 连续 4 次返回 503「服务太忙」 |

`deepseek-pi` 启动更快，但干真实任务时更慢，有时也更细致。日常用 `deepseek`，`deepseek-pi` 作为走 API 的备份。以上每项都只采了一次样。

## 历史

- **2026-11-07：Pi、agy、Vibe 改跑各自的 TUI（v0.12.0）。** `launch`／写完结果／`wait` 的中位数，桥接（修复轮询那一轮）→ TUI：

  | 名字 | 桥接 | TUI |
  | --- | --- | --- |
  | `gemini` | 3.9 / 16.0 / 24.8 | 2.4 / 16.6 / 40.8 |
  | `mistral` | 4.9 / 13.5 / 21.4 | 4.5 / 7.2 / 15.3 |
  | `deepseek` | 4.9 / 7.4 / 12.3 | 4.4 / 10.7 / 15.4 |
  | `deepseek-pi` | 1.4 / 4.4 / 6.3 | 1.9 / 5.3 / 9.3 |

  四个名字的 `launch` 都低于 4.5 秒参考值。`wait` 一列跟着模型收尾走；每个名字只跑了 3 次，看不出趋势。
- **2026-11-07，修复轮询。**
  - **现象：** 修复前，`wait` 返回的时刻扎堆在约 5 秒的整数倍上（10、15、20、25、30 秒）。
  - **原因：** daemon 每轮都对每条非 dead 的会话记录单独起一个 `tmux has-session` 进程探活。约 600 条已结束记录时，这一步每轮要约 2.3 秒，加在 3 秒的固定间隔之上，而且记录越多越慢。
  - **修复：** 每轮只取一次 `tmux list-sessions` 快照；快照本身失败时，才退回逐条探活。某条记录 capture 出错时，会当场重新探活。
  - **效果：**
    - 600 条已结束记录时，一次刷新从 2293 毫秒降到 11 毫秒；
    - 轮询周期从约 5 秒降到约 3.06 秒，daemon 察觉完成的最长等待从约 5 秒降到约 3 秒；
    - 轮询周期不再随记录增多而变长。
- **2026-11-06，第一次测量（修复前）。** 中位数，依次为 `launch` 返回、写完结果、`wait` 返回：
